## 2. Cross-tenant access — ✅ Closed (with caveat below)

For any legacy filename that exists in the DB: the resolver returns the correct owner, and the comparison at L77 enforces session match. **Cross-tenant read is now blocked.**

For any legacy filename that does NOT exist in the DB: resolver returns `null` → 403. **Orphaned files are inaccessible.** This is the correct security posture.

**The R-02 legacy gap from PHASE0-REVIEW.md is closed** for all 7 file-bearing models.

## 3. Query fanout / performance — 🟢 Acceptable for this app

**Characteristics:**
- 7 parallel `findFirst` queries via `Promise.all` on every legacy-path request.
- Each query filters by `filename` (string equality on a non-indexed column).
- SQLite is the DB backend (`DATABASE_URL: file:/data/garage.db`).

**Assessment:**
- For a personal/small-team app, table sizes are low (likely < 10K rows total across all 7 tables). SQLite full-table scan on 7 small tables is sub-millisecond.
- `Promise.all` parallelism is limited by SQLite's single-writer lock, so these will effectively serialize. Still fast.
- As legacy files are accessed less over time (new uploads go to `users/<id>/...` path), this code path becomes progressively rarer.
- **No index needed now.** If this app ever goes multi-tenant at scale, add `@@index([filename])` to the 7 models.

**One improvement suggestion (non-blocking):** add a `console.log` or structured log entry when the legacy resolver is invoked, so operators can track how many legacy-path requests remain. This helps decide when it's safe to remove the resolver entirely.

## 4. 🔴 Required fix: Thumbnail suffix breaks legacy ownership lookup

**The bug:**

When a browser requests a legacy video's thumbnail, the URL is e.g.:
```
/uploads/some-old-video.mp4.thumb.webp
```

The `filename` variable at L66 becomes `some-old-video.mp4.thumb.webp`. This does NOT match the `users/<id>/...` regex, so it falls into the legacy branch (L74).

`resolveLegacyOwnerUserId("some-old-video.mp4.thumb.webp")` queries all 7 tables for a row where `filename = "some-old-video.mp4.thumb.webp"`. **No row stores the `.thumb.webp` suffix** — they store the base video filename (e.g., `some-old-video.mp4`). All 7 queries return null → resolver returns `null` → **403 Forbidden**.

The thumbnail self-heal code at L94–129 never executes because the 403 is returned at L78 before reaching L88.

**Impact:** Every legacy video thumbnail is now broken for all users, including the rightful owner.

**Fix:** Strip the `.thumb.webp` suffix before the legacy DB lookup:

```typescript
} else {
  // For thumbnail derivatives, resolve ownership against the base media filename
  const lookupFilename = filename.endsWith(".thumb.webp")
    ? filename.replace(/\.thumb\.webp$/, "")
    : filename;
  const ownerUserId = await resolveLegacyOwnerUserId(lookupFilename);
  if (!ownerUserId || ownerUserId !== session.userId) {
    return NextResponse.json({ error: "Forbidden" }, { status: 403 });
  }
}
```

This is a 3-line change. The ownership of a thumbnail is always the ownership of its source video.

**Note:** The same pattern should apply to any future derivative suffixes (e.g., `.preview.jpg`), but `.thumb.webp` is the only derivative pattern in the codebase today.

## 5. Minor observations (non-blocking)

### 5a. `(prisma as any)` casts on JobPhoto and PostMedia (L37–38)
These two models use `as any` while the other 5 use typed Prisma calls. This suggests the Prisma client generation may be stale or these models were added after the last `prisma generate`. It works at runtime but loses type safety. **Recommend running `npx prisma generate`** and removing the casts.

### 5b. Short-circuit optimization opportunity
The resolver always runs all 7 queries even if the first one matches. For performance, you could use a sequential early-return pattern instead of `Promise.all`. But given the SQLite serialization and small dataset, `Promise.all` is actually cleaner code and negligibly different in performance. **Keep as-is.**

### 5c. `resolveLegacyOwnerUserId` should be wrapped in try-catch
Currently, if any of the 7 Prisma queries throws (e.g., schema drift, connection failure), the `Promise.all` rejects, and the unhandled rejection bubbles up to Next.js as a 500. This is fail-closed ✅, but:
- No structured log of the error
- The user sees a generic 500 instead of a descriptive error

**Recommend** wrapping the `Promise.all` in try-catch with a log + 403 fallback:
```typescript
try {
  const ownerUserId = await resolveLegacyOwnerUserId(lookupFilename);
  if (!ownerUserId || ownerUserId !== session.userId) {
    return NextResponse.json({ error: "Forbidden" }, { status: 403 });
  }
} catch (err) {
  console.error("[uploads] legacy owner resolution failed", { filename, error: err });
  return NextResponse.json({ error: "Forbidden" }, { status: 403 });
}
```

This keeps it fail-closed but with observability.
