### 1. processingStatus derivation logic — ✅ Correct

**GET endpoint (L92-97):**
```ts
const photosWithStatus = await Promise.all(photos.map(async (p: any) => {
  if (p.mediaType !== "video") return { ...p, processingStatus: "ready" as const };
  const absPath = path.join(process.cwd(), "public", "uploads", `${p.filename}.thumb.webp`);
  const hasThumb = await mediaExists({ relPath: `${p.filename}.thumb.webp`, absPath });
  return { ...p, processingStatus: hasThumb ? "ready" as const : "processing" as const };
}));
```

- Images → always `"ready"`. **Correct** — images don't have a transcode step.
- Videos → check if `<filename>.thumb.webp` exists via `mediaExists` (S3 `HeadObject` or local `readFile`).
  - Thumb exists → `"ready"` (video has been processed)
  - Thumb missing → `"processing"` (worker hasn't run yet, or failed)
- Uses `mediaExists` from CHG-007, which correctly handles both local and S3 backends. ✅

**POST endpoint upload response (L171-175):**
```ts
const processingStatus = isVideo && (!INLINE_VIDEO_TRANSCODE || rawBuffer.length > MAX_INLINE_VIDEO_BYTES)
  ? "processing"
  : "ready";

created.push({ ...photo, processingStatus });
```

- If inline transcode was skipped (flag disabled OR file too large) → `"processing"`.
- Else (inline transcode completed) → `"ready"`.
- Matches the actual behavior from CHG-005. ✅

**Edge case handled correctly:** If the worker has already run on a previously-uploaded video but the GET happens before the client refreshes, the status correctly reflects "ready" because the thumbnail now exists. The status is **derived from current state**, not stored in DB, so it self-corrects.

## Minor observations (non-blocking)

### 6a. Query fanout concern (same as CHG-007 review)

**L92-97:** The GET endpoint now runs a `mediaExists` check (S3 `HeadObject` or local file read) for **every video** in the job's photo collection. If a job has 20 videos, that's 20 parallel S3 API calls.

**Assessment:**
- For personal app with SQLite, typical job has 1-5 photos/videos. Fanout is minimal.
- `mediaExists` calls are in `Promise.all`, so they run in parallel (sub-second total for small counts).
- S3 `HeadObject` is cheap (no data transfer).
- Local file `readFile` for existence check is wasteful (CHG-007 review flagged this) but harmless for small thumbnails.

**Not blocking.** For multi-tenant scale, add a DB column `thumbnailReady: boolean` and update it when the worker runs. But that's Phase 2.

### 6b. Worker should update a DB flag (future improvement)

Currently, status is **derived** from file existence. This works but has a race:
- Worker starts processing video A.
- Worker crashes mid-transcode (ffmpeg fails, OOM, etc.).
- Partial thumbnail file may exist (0 bytes, corrupt).
- `mediaExists` returns `true` → status becomes `"ready"` but thumbnail is actually broken.

**Mitigation for Phase 1:** The worker should:
1. Write thumbnail atomically (temp file → rename).
2. Optionally update a DB column `thumbnailReady: true` after successful write.
3. GET endpoint checks DB column, not file existence.

This makes the status more reliable. Not urgent for Phase 0 since ffmpeg failures are rare and the on-demand thumbnail generator in `/uploads` route can self-heal.

### 6c. "⏳" emoji may not render on all devices

The hourglass emoji (U+23F3) is generally well-supported but may show as a box on older Android/Linux. Consider using a text alternative like "●" or "Processing..." if this becomes a user report. Not blocking.
