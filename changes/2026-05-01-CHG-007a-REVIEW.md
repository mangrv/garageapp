### 1. Does this resolve the CHG-007 blocker? — ✅ Yes

**`package.json:26`:** `"ts-node": "^10.9.2"` is now under `dependencies`, not `devDependencies`.

When `npm ci --omit=dev` or `npm prune --production` runs in a Docker build, `ts-node` will be retained. The script `"media:process-pending": "ts-node scripts/process-pending-media.ts"` (L11) will resolve correctly.

**Also note:** `"db:seed": "ts-node prisma/seed.ts"` (L10) and `"test": "node --import ts-node/register ..."` (L9) also depend on `ts-node`. Moving it to `dependencies` incidentally fixes the seed script in production too, which is a bonus (operators sometimes need to re-seed after a migration).

**Blocker resolved. ✅**

---

### 2. Dependency-policy concerns — 🟢 None blocking

**Image size impact:** `ts-node` + its transitive deps (`@tsconfig/node*`, `acorn-walk`, `arg`, etc.) add roughly **~2–3 MB** to the production image. For a Next.js app image that's typically 200–500 MB, this is negligible.

**Security surface:** `ts-node` is a well-maintained TypeScript execution engine with no network surface. It runs only when explicitly invoked by the npm script. It doesn't listen on ports, doesn't add middleware, doesn't run at app startup. **No runtime security concern.**

**Dependency philosophy note:** The change doc correctly acknowledges this is a "pragmatic stop-gap" and that the long-term preferred approach is precompiled worker JS. I agree — for Phase 1 or Phase 2, compiling `scripts/*.ts` to JS during `next build` and running `node dist/scripts/process-pending-media.js` is cleaner. But for Phase 0 shipped this week, moving `ts-node` to `dependencies` is the right trade-off: zero risk, zero code change to the worker itself, immediate unblock.

**One observation:** `typescript` (L37) remains in `devDependencies`. `ts-node` requires `typescript` as a peer dependency. In a `--omit=dev` install, `typescript` won't be present, and `ts-node` may fail with `Cannot find module 'typescript'`. **However:** Next.js itself bundles TypeScript internally, and most production Docker images retain it because `next build` needs it in the build stage (and multi-stage builds copy the full `node_modules` from the build stage). So in practice this likely works. **Verify with validation checklist item #2** — if it fails, move `typescript` to `dependencies` as well.
