## CHG-007 — Async Pending-Media Worker

### Verdict: 🟡 Approved with two required fixes and notes

The worker is well-structured, idempotent, and operationally sound for a cron-driven single-host model. Two issues need resolution before production use.

---

### 1. Idempotent behavior — ✅ Correct

**Lines 13–14 (`processVideo`):**
```ts
const hasThumb = await mediaExists({ relPath: thumbRel, absPath: thumbAbs });
if (hasThumb) return { skipped: true };
```
- Uses the new `mediaExists` helper which checks S3 (`HeadObject`) or local (`readFile`).
- If thumbnail already exists → skip. **Idempotent. ✅**
- Safe to re-run unlimited times. Verified in change doc validation item #5.

**`mediaExists` implementation (`media-storage.ts:156–175`):**
- S3 path: `HeadObjectCommand` → true/false via try-catch. **Correct.** `HeadObject` is the canonical S3 existence check.
- Local path: uses `readFile` to check existence. **Functionally correct but wasteful** — reads the entire file into memory just to check if it exists. For a thumbnail webp this is fine (< 100 KB), but the function name implies existence-only. **Non-blocking nit:** replace with `stat()` or `access()` for local mode to avoid reading file contents.

### 5. 🔴 Required fix: `ts-node` is a devDependency

**The bug:**
`package.json:11` defines: `"media:process-pending": "ts-node scripts/process-pending-media.ts"`
`ts-node` is listed as a `devDependency` (L36). In a production Docker build that runs `npm ci --omit=dev` or `npm prune --production`, `ts-node` won't be available.

The current `Dockerfile` likely installs all deps for `next build` then prunes — I can't verify without seeing it, but this is a standard pattern.

**Fix options (pick one):**
- **(a) Pre-compile the worker** as part of the build step and run the compiled JS:
  ```json
  "media:process-pending": "node dist/scripts/process-pending-media.js"
  ```
  Add a tsconfig path + build step that includes `scripts/`. This is the cleanest option.
- **(b) Move `ts-node` to `dependencies`** — quick but dirty, adds ~2 MB to the production image.
- **(c) Use `tsx` instead** — lighter than ts-node and handles ESM/CJS better. Still needs to be a production dep.
- **(d) Use `npx ts-node`** — fetches on-demand if missing. Fragile in air-gapped environments.

**Recommendation:** option (a) for production correctness. Option (b) is acceptable as a stop-gap if the Dockerfile doesn't prune devDeps.

### 6. 🟡 Issue: Worker overwrites original video with transcoded version

**Line 19:**
```ts
await persistMedia({ relPath: row.filename, absPath, buffer: optimized.video, contentType: "video/mp4" });
```

The worker reads the raw video, runs `optimizeVideo`, then **writes the optimized video back to the same key** (`row.filename`). This destructively replaces the original upload.

**Is this intentional?** The inline transcode path (CHG-005) does the same thing — `optimizeVideo` returns a transcoded buffer and the route saves it as the same filename. So this is *consistent* with existing behavior. But it means:
- The original raw upload is permanently lost once the worker processes it.
- If transcoding produces a corrupt output, there's no way to recover the original.
- Re-running the worker won't re-process (idempotent via thumbnail check), but a failed transcode that still writes partial output is unrecoverable.

**Assessment:** Acceptable for a personal app where disk/S3 space is a concern and originals aren't needed. But if the user ever wants to re-transcode at a different quality or resolution, the source material is gone.

**Suggestion (non-blocking for now, important for Phase 2):** Write the optimized video to a separate key (e.g., `<original>.opt.mp4`) and update the DB row, preserving the original. Or at minimum, only overwrite if the transcode output is non-empty and passes a basic sanity check (file size > 0, ffprobe validates).

---

### 7. Memory concern for large videos

**Line 16:** `const raw = await readMedia(...)` — reads the entire raw video into a Node.js `Buffer`.
**Line 17:** `const optimized = await optimizeVideo(raw)` — `optimizeVideo` (from `post-media.ts`) writes to `/tmp`, runs ffmpeg, reads the output back into memory.

For a 500 MB raw video, peak memory is roughly: 500 MB (raw buffer) + 500 MB (optimized buffer) + 100 KB (thumbnail) ≈ **~1 GB**. For the Docker container with default memory limits, this could OOM.

**Assessment:** The inline path has the same issue — this isn't new. But the inline path was gated by `MAX_INLINE_VIDEO_BYTES` (50 MB), while the worker processes everything beyond that limit. The whole point of the worker is to handle the big files that the inline path skips.

**Mitigation options (non-blocking for Phase 0, recommended for Phase 1):**
- Process one video at a time (already done ✅ — sequential `for` loop, not `Promise.all`).
- Add a `MAX_WORKER_VIDEO_BYTES` env var to skip truly massive files (e.g., > 1 GB) with a log warning.
- Long-term: stream-based ffmpeg with pipes instead of full buffer reads.

---

### 8. Minor observations (non-blocking)

**8a.** `mediaExists` local path (L169–173) uses `readFile` instead of `stat`/`access`. For thumbnails this is harmless (< 100 KB). For checking existence of a 500 MB video it would be a problem, but the worker only checks thumb existence. **Acceptable, but recommend switching to `stat()` for correctness.**

**8b.** The worker doesn't log a start timestamp or total elapsed time. Adding `console.log("[pending-media] start", new Date().toISOString())` at the top and elapsed time in the summary would help operators judge cron scheduling intervals.

**8c.** `(prisma as any)` casts on `jobPhoto` and `postMedia` (L28–29) — same as in CHG-006b. Recommend `npx prisma generate` to fix.
